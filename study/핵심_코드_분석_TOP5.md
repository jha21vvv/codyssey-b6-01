## Code 1. 외래키(FK) 보안 스위치 활성화

* **소스 파일**: `sql/01_schema.sql` (Line 9)
* **평가관의 체크 포인트**: 
  > *"SQLite는 하위 호환성을 이유로 기본 설정에서 외래키 제약조건 검사가 꺼져(OFF) 있다. 이 사실을 인지하고 DDL 실행 전 최우선으로 켰는가?"*

### 💻 소스 코드 및 2단 주석
```sql
-- [1차]: SQLite 엔진 세션에서 외래키(Foreign Key) 참조 무결성 검증 기능을 강제로 활성화합니다.
-- [2차]: 현관문에 디지털 도어락을 켜지 않으면 엉뚱한 부모 번호를 가진 가짜 미아 데이터가 몰래 들어올 수 있으므로 보안 시스템을 가동합니다.
PRAGMA foreign_keys = ON;
```

### 🔍 세부 기술 해설
* **만약 이 코드가 없다면?**
  * `members` 테이블에 회원 번호가 1번부터 10번까지만 있는데, 어떤 악의적인 요청이나 버그로 `member_id = 9999`인 주문을 넣어도 에러 없이 그대로 DB에 들어갑니다.
  * 부모 없는 고아(Orphan) 주문 데이터가 쌓여 데이터 무결성이 붕괴됩니다.
* **이 코드를 넣었을 때**:
  * 존재하지 않는 부모 ID를 참조하는 순간 `sqlite3.IntegrityError: FOREIGN KEY constraint failed` 예외가 발생하며 쓰기 작업이 완벽히 차단됩니다.
* **내 요약**: 부모(회원, 메뉴)가 없는 유령 자식(영수증, 주문상세)은 절대로 태어나지 못하게 입구를 막는 자물쇠

## Code 2. N:M 해소 교차 테이블 & 스냅샷 불변성

* **소스 파일**: `sql/01_schema.sql` (Line 137~179)
* **평가관의 체크 포인트**: 
  > *"주문(Orders)과 메뉴(Menus)의 다대다 관계를 주문상세 테이블로 잘 정규화했는가? 그리고 메뉴판 가격 인상에 대비해 '결제 시점 단가'를 스냅샷으로 보존했는가?"*

### 💻 소스 코드 및 2단 주석
```sql
-- [1차]: 주문(orders)과 메뉴(menus) 사이의 N:M 다대다 관계를 1:N 2개로 해소하는 교차 테이블을 정의합니다.
-- [2차]: 영수증 속 안쪽에 적히는 "아메리카노 2잔, 케이크 1개"처럼 줄줄이 적히는 세부 구매 품목 목록입니다.
CREATE TABLE order_items (
    -- [1차]: 개별 품목 줄의 고유 식별자 기본키(PK)입니다.
    -- [2차]: 영수증 속 품목 한 줄 한 줄마다 매겨지는 고유 일련번호표입니다.
    -- order_item_id[이름]INTEGER[타입: 데이터를 정수로]PRIMARY KEY[역할]AUTOINCREMENT[옵션: 아이디를 자동발급하도록함]         
    order_item_id INTEGER PRIMARY KEY AUTOINCREMENT,

    -- [1차]: 부모 주문(orders) 테이블의 order_id를 참조하는 외래키(FK)입니다.
    -- [2차]: 이 품목 줄이 몇 번 영수증에 적혀 있는 것인지 묶어주는 영수증 번호표입니다.
    -- 널값은 안되도록 조건을 달아두는 셈. 필수 입력요구
    order_id INTEGER NOT NULL,

    -- [1차]: 부모 메뉴(menus) 테이블의 menu_id를 참조하는 외래키(FK)입니다.
    -- [2차]: 손님이 주문한 메뉴가 메뉴판의 어떤 메뉴인지 가리키는 메뉴 바코드 번호입니다.
    menu_id INTEGER NOT NULL,

    -- [1차]: 주문 수량을 나타내며 0보다 커야 하는 CHECK 제약조건을 가집니다.
    -- [2차]: 음료를 0잔이나 마이너스 잔 시킬 수는 없으므로 무조건 1잔 이상이어야 합니다.
    quantity INTEGER NOT NULL CHECK(quantity > 0),

    -- [1차]: ★[스냅샷 불변성] 주문 발생 시점의 개별 메뉴 단가를 스냅샷으로 영구 보존합니다.
    -- [2차]: 훗날 메뉴판 가격이 5,000원으로 올라도, 이 영수증에는 당시 결제한 4,500원이 종이에 잉크로 박제되어 있어야 회계 사고가 안 납니다.
    unit_price INTEGER NOT NULL CHECK(unit_price > 0),

    -- [1차]: 부모 주문(orders) 삭제 시 연관된 상세 품목들도 함께 자동 연쇄 삭제(CASCADE)합니다.
    -- [2차]: 영수증 원본을 파쇄기에 넣으면 영수증 속 품목 내역 종이도 함께 깔끔하게 파쇄됩니다.
    --오더즈라는 테이블에서 오더 아이디가 같은 행을 보고 있다가 그게 사라지면 같은 오더 아이디를 포린키로 쓰고 있는애들을 따라삭제하라라고 미리 명령 거어둔셈..
    FOREIGN KEY (order_id) REFERENCES orders (order_id) ON DELETE CASCADE,

    -- [1차]: 주문 내역에 존재하는 메뉴를 메뉴판에서 함부로 삭제하지 못하도록 차단(RESTRICT)합니다.
    -- [2차]: 과거 영수증에 버젓이 찍혀 있는 메뉴를 메뉴판에서 완전히 지워버리면 과거 영수증이 훼손되므로 막습니다.
    -- 과거 영수증들(order_items) 중에 이 아메리카노(1번)를 가리키고 있는 영수증이 수백 개나 남아있습니다!과거 거래 내역이 아직 물려있으므로, 메뉴판에서 아메리카노를 삭제하는 것을 절대로 허용할 수 없습니다!(RESTRICT)
    FOREIGN KEY (menu_id) REFERENCES menus (menu_id) ON DELETE RESTRICT
);
```

### 🔍 세부 기술 해설
1. **N:M 다대다 해소**:
   * 주문 1건에 메뉴 여러 개, 메뉴 1개는 여러 주문에 포함됩니다.
   * `order_items`가 양쪽의 PK(`order_id`, `menu_id`)를 외래키로 품음으로써 1:N 2개로 분해했습니다.
2. **`unit_price` 스냅샷 불변성**:
   * "메뉴판에 가격이 있는데 왜 또 적어?"라고 생각하기 쉽지만, 내일 메뉴 가격이 인상되면 과거 영수증 금액까지 뻥튀기되는 대참사가 터집니다.
   * 거래 시점의 단가를 `unit_price`에 복사해 두어 영구 불변성을 보장합니다.

## Code 3. 미구매 고객 발굴용 레프트 조인

* **소스 파일**: `sql/03_queries.sql` (Line 108~124, Q07)
* **평가관의 체크 포인트**: 
  > *"INNER JOIN을 쓰면 주문 없는 회원이 결과에서 증발한다는 사실을 알고, 의도적으로 LEFT JOIN과 IS NULL을 구사했는가?"*

### 💻 소스 코드 및 2단 주석
```sql
-- ------------------------------------------------------------------------------
-- Q07. 한 번도 주문하지 않은 미구매 신규/휴면 회원 발굴
-- ------------------------------------------------------------------------------
-- [1차]: 회원 ID, 이름, 이메일, 가입일 컬럼을 프로젝션(SELECT)합니다.
-- [2차]: 웰컴 감사 쿠폰을 보내드리기 위해 손님의 이름과 가입일자 명단을 뽑아냅니다.
SELECT m.member_id, m.name, m.email, m.created_at
-- [1차]: 회원 명부 테이블(members)을 왼쪽(Left) 기준 테이블로 지정합니다.
-- [2차]: 가입한 모든 고객(m)을 한 명도 빠짐없이 출석부에 세웁니다.
FROM members m
-- [1차]: 주문 테이블(orders)과 LEFT JOIN하여 주문이 없는 회원도 누락 없이 NULL로 유지합니다.
-- [2차]: 각 손님 옆에 그 손님이 결제한 영수증(o)을 올려놓되, 영수증이 없는 손님 자리는 빈칸(NULL)으로 둡니다.
LEFT JOIN orders o ON m.member_id = o.member_id
-- [1차]: 오른쪽 주문 테이블의 order_id가 NULL인 행만 필터링합니다.
-- [2차]: 영수증 자리가 텅 빈(NULL) 손님, 즉 회원가입만 하고 아직 커피를 한 번도 안 사 마신 신규 고객만 콕 집어냅니다.
WHERE o.order_id IS NULL;
```

### 🔍 세부 기술 해설
* **INNER JOIN과의 비교**:
  * `INNER JOIN`을 사용하면 주문 영수증이 있는 활성 고객만 남고, 주문 실적이 없는 신규 회원(9번 장우진, 10번 한예원)은 **결과에서 통째로 증발(삭제)**됩니다.
  * `LEFT JOIN`은 왼쪽 테이블(`members`)을 100% 살려두고 주문 영수증 자리를 `NULL`로 채우므로, `WHERE o.order_id IS NULL`을 통해 잠자는 고객을 기가 막히게 발굴할 수 있습니다.

## Code 4. 결제 취소 제외 및 단골 필터링

* **소스 파일**: `sql/03_queries.sql` (Line 185~214, Q11)
* **평가관의 체크 포인트**: 
  > *"개별 행 필터(WHERE)와 그룹 집계 결과 필터(HAVING)의 물리적 실행 순서 차이를 정확히 알고 분리해서 작성했는가?"*

### 💻 소스 코드 및 2단 주석
```sql
-- ------------------------------------------------------------------------------
-- Q11. 2회 이상 주문한 단골 고객 및 총 결제액 필터링
-- ------------------------------------------------------------------------------
-- [1차]: 손님 이름과 집계 함수로 계산된 총 주문 횟수, 총 결제 금액을 선택합니다.
-- [2차]: 단골 전용 VIP 혜택을 드리기 위해 손님 이름과 방문 횟수를 확인합니다.
SELECT 
    m.name AS member_name,
    COUNT(o.order_id) AS repeat_orders,
    SUM(o.total_amount) AS total_spent
FROM members m
INNER JOIN orders o ON m.member_id = o.member_id

-- [1차]: [WHERE] GROUP BY로 묶기 전에 취소(CANCELLED)된 영수증은 집계 대상에서 미리 제외합니다.
-- [2차]: 손님별로 영수증을 모으기 전에, 도중에 결제 취소한 불량 영수증은 쓰레기통에 먼저 버립니다.
WHERE o.order_status IN ('COMPLETED', 'PAID')

-- [1차]: [GROUP BY] 회원 ID와 이름을 기준으로 바구니(그룹)를 묶습니다.
-- [2차]: 같은 손님의 영수증끼리 모아서 손님 이름이 적힌 바구니에 담습니다.
GROUP BY m.member_id, m.name

-- [1차]: [HAVING] 그룹 집계 결과 중 주문 건수가 2건 이상인 단골 그룹만 최종 통과시킵니다.
-- [2차]: 영수증 바구니를 세어보고 영수증이 딱 1장뿐인 분들은 제외하고, 2장 이상 들어있는 단골 바구니만 건져냅니다.
HAVING COUNT(o.order_id) >= 2

-- [1차]: 주문 횟수 내림차순, 총 결제액 내림차순으로 정렬합니다.
-- [2차]: 가장 매장을 자주 찾아주신 충성 고객 순서대로 맨 위에 줄을 세웁니다.
ORDER BY repeat_orders DESC, total_spent DESC;
```

### 🔍 세부 기술 해설
* **WHERE vs HAVING 역할 분담**:
  * `WHERE`: 원본 행이 살아남을지 결정. 취소된 영수증(`CANCELLED`)을 집계 계산 전에 미리 탈락시켜 연산량을 줄입니다.
  * `HAVING`: 그룹별 집계 결과(`COUNT(o.order_id)`)를 기준으로 필터링. 아직 묶이지도 않은 상태인 `WHERE`에서는 `COUNT`를 쓸 수 없으므로 반드시 `HAVING`에 위치해야 합니다.

## Code 5. 복합 B-Tree 인덱스 및 실행 계획 증명

* **소스 파일**: `sql/03_queries.sql` (Line 251~275, Q15)
* **평가관의 체크 포인트**: 
  > *"인덱스 문법만 알고 있는가, 아니면 실제로 인덱스가 타는지 EXPLAIN QUERY PLAN으로 증명할 줄 아는가?"*

### 💻 소스 코드 및 2단 주석
```sql
-- ------------------------------------------------------------------------------
-- Q15. 복합 인덱스 생성 및 실행 계획(EXPLAIN QUERY PLAN) 분석
-- ------------------------------------------------------------------------------
-- [1차]: orders 테이블의 member_id와 ordered_at 컬럼을 결합한 복합 B-Tree 인덱스를 생성합니다.
-- [2차]: 도서관에서 책을 찾기 쉽게 '손님 회원번호와 주문 날짜'가 적힌 가나다순 빠른 색인 견출지 스티커를 만듭니다.
CREATE INDEX IF NOT EXISTS idx_orders_member_ordered_at 
ON orders (member_id, ordered_at DESC);

-- [1차]: 실행 계획(EXPLAIN QUERY PLAN)을 통해 인덱스가 실제로 사용되는지 옵티마이저 계획을 확인합니다.
-- [2차]: 영수증을 찾을 때 보관함을 처음부터 끝까지 다 뒤지는지(Full Scan), 방금 만든 색인 스티커(Index Scan)를 타고 바로 가는지 돋보기로 검사합니다.
EXPLAIN QUERY PLAN
SELECT order_id, total_amount, ordered_at
FROM orders
WHERE member_id = 1
ORDER BY ordered_at DESC;
```

### 🔍 세부 기술 해설
* **실제 터미널 출력 결과**:
```text
id | parent | notused | detail
---+--------+---------+---------------------------------------------------------------------
4  | 0      | 0       | SEARCH orders USING INDEX idx_orders_member_ordered_at (member_id=?)
```
* **성능적 의미**:
  * 테이블 전체를 무식하게 뒤지는 `SCAN orders` ($O(N)$) 방식이 완전히 사라졌습니다.
  * 복합 B-Tree 인덱스를 타고 곧바로 원하는 손님의 최신 영수증으로 직행하는 **`SEARCH orders USING INDEX` ($O(\log N)$)** 방식으로 동작함을 공식 증명했습니다.

## 💡 한눈에 보는 핵심 평가 포인트 체크리스트

| 검증 항목 | 대상 코드 | 핵심 가치 및 의미 |
| :--- | :--- | :--- |
| **참조 무결성 보장** | `PRAGMA foreign_keys = ON;` | 가짜 부모 번호를 가진 고아 데이터 삽입 원천 차단 |
| **다대다 정규화 & 불변성** | `order_items` (with `unit_price`) | 주문-메뉴 N:M 분해 및 메뉴 가격 인상 시 과거 결제액 불변성 보존 |
| **데이터 증발 방어** | `LEFT JOIN` + `IS NULL` | 주문 실적이 없는 신규 회원도 누락 없이 마케팅 타겟으로 발굴 |
| **쿼리 파이프라인 준수** | `WHERE` + `GROUP BY` + `HAVING` | 개별 행 필터(WHERE)와 그룹 집계 필터(HAVING)의 시간 순서 완벽 분리 |
